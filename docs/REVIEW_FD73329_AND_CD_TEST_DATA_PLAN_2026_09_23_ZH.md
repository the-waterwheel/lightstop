## 2. 本轮需修改的发现

### R1 / P1：退后台可能留下永久的 Zone 忙状态

位置：`MainActivity.onMeteringRestoreStateChanged()`、`onPause()`；`MeterModels.meteringInteractionBusy`；`ZoneSystemView.canStartCapture()`。

触发顺序：

1. 结果交付后恢复开始，`state.meteringInteractionBusy=true`。
2. 恢复完成前按 Home / 暂停 Activity。`onPause()` 清了 `zoneCameraRestorePending`，却没有清新的 state 字段。
3. 恢复完成回调若在后台到达，会被 `if (!activityResumed) return` 丢弃；控制器关闭也可能直接取消该事务，不再产生恢复完成事件。
4. 返回同一个 Activity，View 仍读到 busy=true，点按和长按建点被阻止；Activity 私有忙判据却已经为 false，形成两份状态不一致。

修改要求：

- 在暂停/取消/关闭和受控失败终结时同步收尾，不只等待正常 restore=false 回调。
- 最好统一派生资源忙状态，不让 Activity 私有字段和 MeterState 各有独立真值。
- 旧事务的迟到 restore=false 不能清掉新事务的 busy；需要操作身份或等效生命周期过滤。
- 保留结果交付后停圈，不能通过重新绑回 measuring 来规避问题。

必补测试：restore=true → pause → 后台 restore=false 被丢弃 → resume；事务在关闭时取消；下一次点测和全部重测都可操作；旧回调不影响新操作。本轮为代码路径审阅，未进行手机复现。

### R2 / P2：实际路由身份只在内存中使用，缓存仍会跨路径继承确认

位置：`CameraOpenConfiguration.confirmationRouteIdentity()`、`CameraController.openCamera()` 缓存确认分支、`CameraCombinationSelectionStore`。

当前 store 的选择模型仍只有 planId/origin，缓存仍按目录 cameraId 保存。重开读取旧 plan 后，控制器不是比较“探测时保存的实际身份”和“当前身份”，而是直接用当前 `confirmationRouteId()` 新建 CONFIRMED。原本在路径 A 探测的缓存，到了同一目录镜头的路径 B，仍会被重新标记为 B 已确认。

修改要求：保存探测时实际身份，读取后先比较，再恢复确认；未知/不符走显式待验证流程，不能伪造当前路径的成功记录。普通同路径重开、Normal/Zone 各阶段仍保留确认，不把临时 session generation 当作永久身份。

测试不能只比较两个 identity 字符串不同。必须经过：路径 A 探测 → 写缓存 → 关闭 → 路径 B 读缓存 → 不继承确认；同路径则保留。覆盖系统和手动两类缓存、流尺寸变动、老 schema 迁移。

### R3 / P2：旧手动 RAW 缓存变为未确认后，没有补验证流程

位置：`CameraController.openCamera()` 的 storedManualSelection.origin 判断及 pendingSystemWorkflowProbePlanId 分支。

上一版成功手动确认写入的 origin 是 MANUAL。新版本仅认可 MANUAL_VERIFIED，但仍继续使用旧手动 plan；manualPlanRequested=true 又阻止系统探测启动。结果是旧手动 RAW 照常运行却丢失确认保护，运行时失败可能重新进入兼容测光回退分支。

这是升级兼容缺口，不宜通过直接把全部 MANUAL 当作已验证来修补，因为历史格式无法可靠区分验证凭证。应保留用户选择，并显式进行当前路由的重新验证或提示用户重新确认；验证期间不要把一次失败悄悄改为 YUV。

必补测试：用旧版 MANUAL/raw_split_v1 缓存升级，不清数据；保留镜头和模式；验证成功才写 MANUAL_VERIFIED；验证失败/取消不能伪造确认，也不能静默降级。既有 9 月 22 日设备测试留下的手动选择即属于需要考虑的迁移输入。

### 其他未关闭边界

- manualProbeSucceededPlanId 仍只绑定 plan ID，成功回调仍异步写入，缺少探测代次和实际路由凭证；应补取消、重入、迟到成功的集成测试。
- store 的旧兼容注释与当前“无 sample 不更新”的实现不再一致；同时有效更新数为零时不能凭空增加校准历史。应用主要入口已改善，但应进一步测试存储层边界。
- 本批次没有修改 AE 等待和曝光目标调度，不能声称 C / D 已完成。

## 3. C 和 D 是否需要测试数据？

都需要，但先后关系不同。

| 批次 | 是否可以先开发 | 数据的作用 | 放行条件 |
| --- | --- | --- | --- |
| C：曝光目标调度、阶段计时 | 可以。先按明确状态机实现，并补可控回调测试 | 证明结果、停圈、会话恢复、目标生效的顺序及耗时 | 异常/取消有界，旧目标不覆盖新目标，测光圈与资源锁独立；实机日志验证 |
| D：AE 等待与快路径优化 | 可以搭建关闭状态的策略框架；不能无数据直接默认放行快路径 | 确定等待实际原因，并证明提速不损害测量 | C 的基线数据齐备，修改后 A/B 耗时改善且测量一致性/重复性不劣化 |

因此正确顺序是：先修 R1–R3 → 实现 C 的调度与埋点 → 收集当前慢路径基线 → 决定 D 的具体策略 → 在同样条件下复测。不是先凭感觉缩短 1200 ms，然后让测试寻找理由。

## 4. 已有数据与缺口

## 5. C 阶段应先实现的数据记录契约

由实现模型编写；测试方检查字段和实际输出。不需要先保存照片或 RAW 文件，也不需要界面截图。

### 5.1 每次事务的关联身份

`operationId`、页面模式、预览开关、planId、目录镜头 ID、实际路由身份、配置 physical ID / 活动 physical ID、camera generation、session revision、baseline generation、preview target revision、输出尺寸、APK hash/commit、系统构建。

持久确认身份与临时操作代次各有用途，不可混为一个键。所有结果字段缺失时写 null/unknown，不填伪造默认值。

### 5.2 事件时间线

| 事件 | 解决的问题 |
| --- | --- |
| requestAccepted | Normal 和 Zone 统一点击/请求接受起点 |
| neutralRequestSubmitted、firstTaggedResult | 区分请求排队和 AE 本身收敛 |
| baselineFinished(reason) | 区分稳定、超时、取消、无需等待 |
| rawConfigureBegin/End、rawFirstPair | 将切会话、曝光/传输与处理分开 |
| analysisDone、resultPosted、resultUiAccepted、spinnerOffDrawn | 区分算法完成、主线程排队和实际停止绘制转圈 |
| restoreDone | 相机资源重新可用时间，不等于结果生成时间 |
| previewTargetSubmitted、targetResultSeen、textureSeen | 区分请求发出、硬件参数生效和纹理消费；没有可靠帧关联时明确未知 |

本地阶段统一用同一单调时钟。传感器 timestamp 仅在确认对应时钟域后参与关联，不能直接与本地时钟相减。

### 5.3 基线窗口的有限逐帧诊断

仅在本次等待窗口记录：tag、frame number、AE mode/state/compensation、曝光时间、ISO、frame duration、元数据来源、是否通过身份校验、稳定计数/拒绝原因。只开诊断构建或受控开关，限制频率和缓存，不长期全量刷逐帧日志。

### 5.4 结果汇总

每笔包含：RAW 帧数、实际捕获 time/ISO/光圈、sceneEV100、噪声指标、采样有效性、质量动作、ROI/几何身份、校准签名/修正版本、是否超时/重采/取消、batch updated/skipped 及原因。

不能只记录“测光完成用了多少秒”，否则无法区分少拍了帧、跳过校验或实际调度优化。

## 6. D 的采样方案与数据判读

### 6.1 第一轮：主摄小矩阵

保持固定手机、固定目标和尽量稳定光源；不改用户校准。Normal/Zone × 预览 OFF/ON × 明亮/弱光，每组先 10 次，总计 80 笔；可以拆成多轮，不要求用户一次完成。开关/镜头切换后的第一笔单列为过渡样本。以 OFF→ON→OFF 或交替小组降低环境漂移影响。

这只是定位/初筛样本量，不承诺 10 次能可靠估计 P95。先列全部样本、样本数、中位数、最大值、超时/失败数；要做稳定尾部指标，需要后续增加重复次数。

### 6.2 安全边界与扩展

再覆盖：遮住/移开、曝光预览明显正负偏置、低纹理、LED 闪烁、快速目标变化、主摄/超广/长焦、逻辑镜头活动物理变化、前后台恢复。

先一台设备验证因果，再增加其他厂商/版本；不能凭单台 vivo 数据给所有品牌统一写阈值。失败、跳过和超时样本不能从性能统计中删除。

### 6.3 一致性与准确性区别

- 稳定场景比较修改前/后、OFF/ON 的 EV 差异及重复波动，同时控制 ROI、实际镜头、校准状态和光源漂移。
- 无标准测光参考时只能证明一致性/重复性，没有资格宣称绝对精度提升。
- 允许误差应在看优化结果之前，依据项目目标和基线重复性约定；不要事后放宽门槛换取通过，更不能增加固定 EV 补偿掩盖偏差。
- 当快路径依赖旧曝光样本时，突然场景变化必须能返回安全的同源慢路径；不能自动换 YUV、清 RAW 确认或污染校准。

## 7. 给实现模型的下一步指令

1. 先修 R1，补生命周期和请求拒绝测试；修 R2/R3 时把真实身份、缓存迁移、探测凭证作为一条完整链处理。
2. 实现 C 的状态调度和上文日志字段，不需要等待大规模设备数据才开始；默认保持当前测量算法。
3. 交付测试 APK、准确源码提交/hash、日志格式说明、单测结果。不要先默认开启 D 快路径。
4. 测试方组织分轮采集并判断瓶颈；数据足够后，再给 D 下达针对性的修改方案。
5. 源码、APK 和日志一一对应。文档/诊断日志在打包源集外；不清数据、不改校准、不推送发布。

当前结论：校准保护较上版进步，Zone 和确认缓存仍需收尾；C 可先实施用于产出可靠数据，D 必须受数据和测量正确性约束。本轮没有对新提交作真机放行。
